# Sherpa Process Skill

Статус: **фаза 0 (каркас)** — планы и схема готовы, генератор в разработке.
Канонические источники: `PLAN.md` (статус фаз), `main.md` (мастер-контекст проекта).

## Что делает скил

По описанию пользователя собирает Process IR (JSON) и детерминированно компилирует его в `.process` XML для Sherpa RPA, с двухслойной валидацией и профилями draft / release / strict.

## Железные принципы

1. **Модель никогда не пишет `.process` XML руками.** Агент работает только с IR (JSON); генерацию, сериализацию бинарных контейнеров и валидацию выполняет код из `scripts/`. Не декодировать Base64-контейнеры вручную — для этого `inspect`.
2. **Confirmed-over-invented.** Не подтверждено golden-эталоном — не генерируется. Вместо неподтверждённого действия ставится блок `ToDo` (только в draft) и запись в unresolved registry. Никогда не подставлять «похожий» блок.
3. **Детерминизм.** Одинаковый IR → байт-в-байт одинаковый XML (UUIDv5, фиксированный порядок элементов/атрибутов/коннекторов).
4. **Разделение валидации.** Schematron (`schemas/sherpa-rules.sch`) — только структура и шаблоны блоков; Python-валидатор — Base64, бинарные контейнеры, выражения, типы, ссылки, детерминизм; release-профиль объединяет оба отчёта.

## Workflow (целевой, для фазы 6)

```text
уточнить требования → cli.py init-ir → заполнить IR (JSON, не XML!)
→ cli.py build --mode=draft → разобрать отчёт валидации
→ устранить ошибки или зафиксировать ToDo в unresolved registry
→ cli.py validate --profile=release → .process
```

## Справочники (читать по требованию)

- Форматы сериализации: `references/text-serialization.md`, `references/datatable-serialization.md` (будут созданы в фазе 1 из golden).
- Каталоги блоков/типов: `references/block-catalog.yaml`, `references/type-catalog.yaml` (фаза 2).
- Правила валидации: `schemas/sherpa-rules.sch` + `references/schematron-rules.md`.
- Полный мастер-контекст: `main.md`.

## Что делать с неизвестными конструкциями

Если пользователь просит блок/тип/операцию, которых нет в каталоге, — не выдумывать XML. Поставить `ToDo`, записать intent в unresolved registry и предложить пользователю создать golden-образец в Sherpa Designer (запрос по чек-листу `golden/REQUEST.md`), чтобы расширить подтверждённую базу.

## Расширение базы знаний (Extension Pipeline)

**Новый блок из .process**: пользователь принёс файл с незнакомым блоком → запустить
`python scripts/dev/ingest_block.py FILE.process [golden-имя]` (dev-venv). Скрипт скопирует
файл в `golden/real/`, перегенерирует каталоги и покажет готовые строки для `ir.NODE_TYPES`
(логическое имя выбираешь ты; после правки — `pytest tests/unit -q` зелёный). Блок мимо
golden в генератор не попадает.

**Эталонные паттерны** (`patterns/*/pattern.json`) — проверенные golden-ом конструкции из
нескольких блоков (retry-обёртка TryCatch, цикл-счётчик While и т.п.). Когда логика запроса
совпадает с паттерном: прочитай его, вставь `fragment` в IR нового процесса (уникальные ключи
узлов + стыковка по `meta.entry` / `meta.exit` / `body_slot`), параметры-переменные переименуй
под контекст. Новые паттерны: `scripts/dev/extract_pattern.py FILE.process NAME [ID-префиксы]`
даст raw-черновик из golden → нормализуй в логический IR → статус `confirmed` → тесты.
Черновики (`DRAFT-extracted`) не использовать — только `confirmed`.
