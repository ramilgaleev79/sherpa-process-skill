# Синтез графа из задачи (вместо копирования паттернов)

Каталога готовых заготовок в скилле нет: каждый паттерн — **решение конкретной
задачи** со своими числами (`EndIndex=5`, `Limit=3`, `NumberAttempts=3`), порядком
блоков и обработкой ошибок; вставленный целиком фрагмент приносит чужой алгоритм
в новую задачу.

Правило: **алгоритм выводится только из текста задачи**. Ниже — таблицы, по которым
граф собирается с нуля: какие конструкции бывают, как соединяются порты, что проверить.

---

## Протокол: 6 шагов (у каждого — артефакт)

### Шаг 1. Алгоритм словами — таблица шагов

Таблица описывает **алгоритм, а не блоки**. Строка — это шаг, который можно проверить
словами задачи. Блок или конструкция появляются только в последней колонке, и
соответствие не всегда один к одному.

| № | Шаг из задачи | Тип | Что нужно на входе | Конструкция или блок | Почему так |
|---|---|---|---|---|---|
| 1 | «5 скриншотов» | повтор | — | `For 1..5` | число известно заранее |
| 2 | «сделать скриншот» | действие | — | `MakeScreenshot` | один блок |
| 3 | «третий» | условие | индекс итерации | `Condition` `$Индекс -eq 3` | две ветки |
| 4 | «отправить по почте» | действие (Yes) | файл | `SendMailMessage` | один блок |
| 5 | «4 и 5» | условие | индекс итерации | `Condition` `$Индекс -ge 4` | диапазон одним условием |
| 6 | «сохранить на диск» | действие (Yes) | файл, папка | `GetPathFileName` + `CopyItem` | `тех.`: нужен путь |

Типы строк: **действие / условие / повтор / ошибка / данные**.
Пока таблица не готова — блоки не выбираются. Это защита от «знакомого» паттерна.

#### Как резать задачу на строки

1. **Один глагол с одним результатом — одна строка.** «Отправить письмо» — строка;
   «отправить письмо и сохранить копию» — две строки.
2. **«если / когда / в случае» — отдельная строка-условие**; ветки — свои строки
   с пометкой `Yes` / `No`.
3. **«N раз», «для каждого», «пока» — строка-повтор**; всё, что делается внутри,
   идёт ниже с отступом (тело).
4. **«в конце», «после этого» — строка после цикла.** Это определяет, куда идёт `Next`.
5. **«повторить при ошибке», «если упало» — строка-ошибка.**
6. **Данные.** Если в задаче есть отдельное действие («взять таблицу», «измерить размер») —
   это строка. Если нет — это колонка «что нужно на входе» у шага.
7. **Технические строки (`тех.`).** Иногда фразу нельзя выразить одним блоком:
   «если файл больше 500 КБ» требует сначала «узнать размер», потом «сравнить».
   Промежуточный шаг помечается `тех.` — он **ничего не добавляет к задаче**, а только
   делает шаг выразимым. Это единственный законный способ добавить строку сверх цитаты.

#### Как таблица соответствует блокам и конструкциям

| Тип строки | Во что превращается | Соответствие |
|---|---|---|
| действие | один блок библиотеки | 1 : 1 |
| действие с подготовкой | блок + вспомогательные блоки (путь, размер) | 1 : N, помечается `тех.` |
| условие | конструкция `Condition` | 1 : 1; ветки — отдельные строки |
| повтор | `ForLoop` / `ForeachRows` / `ForeachList` / `WhileLoop` | 1 : 1; тело — строки ниже |
| ошибка | `TryCatch` либо свойства блока (`ErrorLevel`, порт `Error`) | 1 : 1 |
| данные | переменная в `variables`, не блок | 1 : 1 |

**«Один блок на строку» — не правило.** Правило двойное: у каждой строки есть цитата из
задачи, которая её породила; у каждого блока — строка, которую он выполняет. Блок без
строки — лишний; строка без блока — `ToDo`.


### Шаг 2. Конструкция по признаку в задаче

| Признак в задаче | Конструкция | Почему |
|---|---|---|
| «5 раз», «N снимков», «три попытки» | `ForLoop` (1..N) | число известно заранее |
| «для каждого», «по каждой строке», «для всех файлов» | `ForeachRows` / `ForeachList` | одна итерация на элемент |
| «пока», «до тех пор, пока», «каждые N минут, пока не…» | `WhileLoop` | условие, а не диапазон |
| «если», «в случае», «когда» | `Condition` | два выхода Yes/No |
| «если … иначе если …» | цепочка `Condition` | `No` → следующий `Condition` |
| «повторить при ошибке», «N попыток» | `TryCatch` | NumberAttempts из задачи |
| «продолжить, даже если шаг упал» | `ErrorLevel=Handle` + порт `Error` | обработка на блоке |
| «прервать робота при ошибке» | порт `Error` → `Stop`/`FullAbort` | терминальный выход |
| ничего из перечисленного | **не добавлять** | лишняя конструкция = чужой алгоритм |

### Шаг 3. Блоки под каждую строку таблицы

- искать по глаголу из задачи: `python scripts/block_suggest.py "отправить письмо"` —
  корпусный индекс (`assets/verb_block_index.json`) даёт кандидатов с частотами;
  выбор — по `block_index.json` (752 блока) и тексту задачи.
- выходные свойства блока (`Result`, `ScreenshotFile`, `SentEmail`) — это уже переменные; не выдумывать новые.
- нет блока → `ToDo` с названием действия (не «похожий» блок).
- блок есть в корпусе, но не в каталоге (`LaunchChrome`) — `block_suggest` помечает
  его отдельно: такие блоки не выбираются.
- значений нет в задаче → пустые переменные-заготовки.

### Шаг 4. Связи — по таблице портов

| Блок | Вход | Вход тела | Возврат тела | Выход |
|---|---|---|---|---|
| `For` | `Input` | `Index` → первый блок тела | последний блок → `For.Input` | `Next` |
| `While` | `Input` | `Iteration` → первый блок | последний блок → `While.Input` | `Next` |
| `ForeachRows` | `Input` | `Row` → первый блок | последний блок → `ForeachRows.Input` | `Next` |
| `ForeachList` | `Input` | `Item` → первый блок | последний блок → `ForeachList.Input` | `Next` |
| `Condition` | `Input` | `Yes` / `No` — ветки | — | `Yes`, `No` |
| `TryCatch` | `Input` | `Next` → тело | — | `Out` — успех, `Error` — ошибка |
| `ProcessContainer` | `Input` | — | — | `Next`, `Error` |
| `Comment` | нет портов | — | — | — |

Правила проводки (проверены по корпусу установки):

1. Тело входит **в `InputLeft`** первого блока (допустим `Input`); так же подключаются ветки `No`.
2. Последний блок тела возвращается в **`Input`** цикла; выход из цикла — `Next`.
3. Один выход = одна связь (`MaxOut=1`); вход допускает много связей (`Input/InputLeft`).
4. `Yes`/`No`, `Index`/`Next`, `Iteration`/`Next`, `Row`/`Next`, `Out`/`Error` — обязательные выходы: неподключённый выход блокирует release.
5. Декоративные блоки (`Comment`) в поток не включаются.

### Шаг 5. Ошибки — из текста задачи, а не «на всякий случай»

| В задаче | Настройка |
|---|---|
| ничего про ошибки | оставить `ErrorLevel=Default` |
| «продолжить работу» | `ErrorLevel=Handle` на конкретном блоке |
| «повторить N раз / подождать» | `TryCatch`: `NumberAttempts`, `PauseBetweenAttempts` — из задачи |
| «остановить робота» | `Error` → `Stop` (или `FullAbort`) |
| «сообщить об ошибке» | `Error` → `SendMailMessage` / `Log` |

### Шаг 6. Проверка (до и после сборки)

1. `python scripts/cli.py validate-ir my.ir.json --profile release` — 0 ERROR.
2. `build` — файл + отчёт; детерминизм проверяется автоматически.
3. Трассировка на бумаге, минимум 3 сценария: успех, ошибка, граница (0 итераций, последняя итерация).
4. Сверка с таблицей шагов: **каждый блок соответствует строке задачи**; лишних блоков нет.

## Механическая сборка: `plan.json` → IR

Таблица шагов может быть входным файлом, а не рисунком: `scripts/dev/plan_to_ir.py`
компилирует её в IR и **сам делает проводку портов** — ручных ошибок в связях не остаётся.

```bash
python scripts/dev/plan_to_ir.py plan.json my.ir.json --print-graph   # таблица → IR
python scripts/dev/plan_to_ir.py plan.json --check                    # проверка под release
python scripts/dev/plan_to_ir.py plan.json --check --profile draft    # если в плане есть ToDo
python scripts/cli.py build my.ir.json my.process --mode release      # дальше обычная сборка
```

Схема плана: `process.name`, `variables[{name, sherpa_type, initial}]`, `steps[]`.
Шаг: `id`, `quote`, `type` и поля по типу.

| type | поля | во что превращается |
|---|---|---|
| `action` | `block` + `props`, `on_error[]`? | узел блока; `on_error` — выход `Error` → свои шаги |
| `action` | `todo` вместо `block` | узел `ToDo` |
| `condition` | `expr`, `then[]`, `else[]` | `Condition` (Yes/No) |
| `repeat` | `kind=for`: start/end/step/index; `while`: expr; `foreach_rows`: table/row/index; `foreach_list`: items/item; `body[]` | цикл |
| `try` | `body[]`, `on_error[]`, `attempts`, `pause` | `TryCatch` |
| `terminal` | — | `Stop` |
| `data` | `declare[]` | переменная (без узла) |

Проводка — автоматическая и детерминированная:

- тело цикла: `Index` / `Iteration` / `Row` / `Item` → `InputLeft` первого блока тела;
- последний блок тела → `Input` цикла; выход из цикла → `Next`;
- `Yes` → `Input`, `No` → `InputLeft`;
- `TryCatch`: `Next` → тело, `Out` → продолжение, `Error` → `on_error`;
- `terminal` — только последним в последовательности; если в конце плана нет терминала,
  добавляется `__stop`.

Коды ошибок плана: `PLAN-001` id · `PLAN-002` цитата · `PLAN-003` тип шага ·
`PLAN-004` выражение · `PLAN-005` блок · `PLAN-006` тело и параметры повтора ·
`PLAN-007` props · `PLAN-008` свойство блока · `PLAN-009` переменная ·
`PLAN-010` объявления · `PLAN-011` пустой план · `PLAN-012` терминал · `PLAN-013` контракт IR.

Пример: `tests/fixtures/plan-screenshots5.json` (задача «5 скриншотов»); покрытие —
`tests/unit/test_plan_to_ir.py` (14 тестов).

## Пример: задача, собранная с нуля

> «Сделать 3 скриншота. Если файл больше 500 КБ — отправить письмом, иначе удалить.
> В конце записать итог в лог.»

**Таблица шагов** (цитата → тип → конструкция или блок)

| № | Шаг из задачи | Тип | Что нужно | Конструкция или блок |
|---|---|---|---|---|
| 1 | «3 скриншота» | повтор | — | `For 1..3` |
| 2 | «сделать скриншот» | действие | — | `MakeScreenshot` |
| 3 | «файл больше 500 КБ» → узнать размер | действие, `тех.` | путь к файлу | `GetFileLength` |
| 4 | «если больше 500 КБ» | условие | размер | `Condition` (Yes/No) |
| 5 | «отправить письмом» | действие (Yes) | размер > порога, файл | `SendMailMessage` |
| 6 | «иначе удалить» | действие (No) | файл | `RemoveItem` |
| 7 | «в конце записать итог» | действие (после цикла) | — | `Log` |

Строка 3 — `тех.`: в задаче не сказано «измерь размер», но без готового числа условие
не выразить одним блоком. Строк «на всякий случай» (лишние паузы, логирование) нет.

**Связи** (только по таблице портов, без паттернов):

```
Start.Next            → For.Input
For.Index             → MakeScreenshot.InputLeft        (тело)
MakeScreenshot.Next   → GetFileLength.Input
GetFileLength.Next    → Condition.Input
Condition.Yes         → SendMailMessage.Input
Condition.No          → RemoveItem.InputLeft
SendMailMessage.Next  → For.Input                        (возврат тела)
RemoveItem.Next       → For.Input                        (возврат тела)
For.Next              → Log.Input                        (после цикла)
Log.Next              → Stop.Input
```

Пример проверен на этой сборке: `validate-ir --profile release` — 0 замечаний,
`build` — OK, прогон сгенерированного файла — все блоки совпали с библиотекой.
IR собирается из таблицы шагов и таблицы портов выше — готовый файл не нужен.

## Корпус: описания + готовые .process

Если есть пары «описание задачи ↔ готовый `.process`», механизм калибруется на фактах,
а не на догадках. Два инструмента.

### `graph_compare.py` — метрика алгоритма

Сравнивает эталон и проверяемый граф по двум слоям: типы блоков и связи
`тип:порт → тип:порт`. Оценка 0…1, порог по умолчанию 0.8, код возврата 1 ниже порога —
годится для приёмки и CI.

```bash
python scripts/dev/graph_compare.py эталон.process мой.process
python scripts/dev/graph_compare.py эталон.process plan.json --json --threshold 0.9
```

Показывает score, расхождения по блокам и связям, число циклов и условий.
Сравнивать «эталон ↔ собранный» полезнее, чем проверять только валидность файла.

### `corpus_mine.py` — что корпус говорит о правилах

```bash
python scripts/dev/corpus_mine.py --corpus corpus/ --out insights.json
```

Раскладка корпуса: `<stem>.process` (или `.ir.json`) + `<stem>.md` с описанием.
Извлекается:

- **глагол → блок** по `DisplayName` узлов (сильный слой) и по описанию документа (слабый);
- **цепочки** `A → B` по связям `Next`;
- **конвенции портов** (`No → InputLeft` и подобные);
- **частота конструкций** (циклы, условия, контейнеры).

### Особенности реальных корпусов Sherpa

Проверено на трёх каталогах установки (`Designer\Library`, `Frameworks`, `Projects`):
**138 процессов, 1869 блоков, 1865 связей** (снято на момент этой серии).
Текущий `replay_corpus.py` по всему `%APPDATA%` видит **208 файлов, 2529 инстансов**;
цифры ниже относятся к исходной серии из 138 процессов.

- **Описание лежит внутри `.process`** — в `Comment`-блоках (текст в `DisplayName`,
  берутся от 40 символов) и изредка в корневом `Description`. Отдельный `.md` не нужен:
  описание нашлось у **105 из 138** процессов.
- **Старые версии блоков — норма.** 1155 из 1869 блоков (62 %, 134 файла) старше
  установленной библиотеки. Такой блок помечается `legacy`: структуру и порты по нему
  читать можно, а свойства — сверять с текущим шаблоном.
- **Блоки, которых больше нет** (20 вхождений: `LaunchChrome`, `LaunchIE`, `NewFile`,
  `RecognizeCaptcha`, `InternalBrowserGet`) помечаются `unknown`, и к ним подставляется
  замена: `LaunchChrome → LaunchBrowser`, `NewFile → OrchStorageCreateFile` и т.д.
- **Разрывы связей.** `dangling` — связь на несуществующий ID (в этих корпусах 0);
  `isolated` — блок без связей. Комментарии намеренно не связаны и разрывом не считаются:
  из 164 «изолированных» 158 — комментарии, реальных 6.

Запуск по трём корпусам сразу:

```bash
python scripts/dev/corpus_mine.py --corpus \
  "%APPDATA%\Sherpa RPA\Designer\Library" \
  "%APPDATA%\Sherpa RPA\Frameworks" \
  "%APPDATA%\Sherpa RPA\Projects" --out insights.json --min-count 2
```

### Замер: описание → план → score

Прогон по `Projects` (61 процесс, описание есть у 25–28). План строит
`plan_from_text.py` — правила без модели (глаголы, «N раз», «если», «для каждого»).

| Вариант | mean | median | max | блоков: план / эталон |
|---|---|---|---|---|
| правила без модели | 0.030 | 0.031 | 0.111 | 1.3 / 14.3 |
| план от модели (3 процесса) | 0.37–0.59 | — | 0.592 | 6–10 / 9–11 |

Вывод: описания в корпусе — уровня «что делает робот», а не «какими шагами».
Одно предложение описывает 9–20 блоков, поэтому текстовый baseline физически не может
восстановить структуру: его score — нижняя граница, а не оценка методички.
Для генерации таблицу шагов берут из текста задачи, а корпусные описания — для поиска
похожего эталона (retrieval) и для калибровки правил, а не для декомпозиции.

### Как это меняет работу

1. **Правила Шагов 2–4 калибруются.** Если в корпусе «сохранить» в 80 % случаев даёт
   `GetPathFileName → CopyItem`, это аргумент для `тех.`-строки, а не догадка.
2. **Результат становится измеримым:** score и диффы вместо «на глаз».
3. **Регрессии ловятся:** новое изменение не должно уронить score на эталонных парах.
4. **Поиск по эталонам:** ближайший по описанию процесс — источник структуры, но числа,
   условия и тела по-прежнему берутся из задачи.

### Eval-пары: качество генерации фиксируется числом

Пары «задача → план → эталон» лежат в `tests/fixtures/evals/` и гоняются
`pytest tests/unit/test_evals.py`: план компилируется в IR, собирается `cli build`
и сравнивается с эталоном через `graph_compare` (порог — в `eval.json` пары).
Три пары: диаграмма из Designer (`best-screenshots`), фиксированная
release-сборка (`screenshots5`), верхний уровень многослойного сервиса
(`ocr-skeleton`; эталон — профиль графа из `scripts/dev/extract_skeleton.py
--depth 0`, поэтому 5 МБ процесса не копируются в репозиторий). Правка правил
или компилятора, уронившая структуру, роняет тест; порог пары — её собственный
(см. `note` в `eval.json`: почему не 1.0).

### Ограничения (честно)

- Сопоставление «фраза ↔ блок» по описанию — документное; точное выравнивание требует
  разметки. Сильный сигнал даёт `DisplayName` блоков.
- Эталон мог быть собран с `ToDo` (блоков тогда не было) — сравнивайте с
  `--ignore ToDoBlock` или пересоберите эталон.
- Метрика измеряет **структуру**, а не бизнес-смысл: разные алгоритмы иногда дают
  высокий score. Это инструмент приёмки, а не доказательство правильности.
- Правила, выведенные по старым версиям блоков, годятся для структуры и портов, но не
  для свойств: у `legacy`-блока набор свойств мог измениться.

## Если под рукой чужой .process или пример из сети

1. Из него берут **только устройство связей**: какой порт куда идёт.
2. Числа, условия, тела и порядок блоков — из задачи, а не из примера.
3. Контрольный вопрос по каждому блоку: «какую строку задачи он выполняет?»
