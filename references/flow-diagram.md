# Блок-схема `.process` с размеченными багами (`flow_diagram.py`)

Инструмент отвечает на вопрос «покажи на схеме, где баг и как его исправить».
Он закрывает ручную работу, которая иначе каждый раз делается заново: по графу
`.process` рисуется HTML-схема, а поверх — нумерованные метки: **красные** —
где баг, **зелёные** — как исправить (какой блок менять / какой блок вставить).

```bash
# схема структуры без багов (навигация по чужому процессу)
python scripts/flow_diagram.py FILE.process

# схема с размеченными багами: красное — где, зелёное — фикс
python scripts/flow_diagram.py FILE.process --findings bugs.json

# самопроверка детерминизма (два рендера обязаны совпасть байт-в-байт)
python scripts/flow_diagram.py FILE.process --findings bugs.json --check
```

Выход: `FILE.flow.html` рядом с входом (или `--out`). Файл самодостаточный —
чистый SVG + CSS, без JavaScript и без внешних ресурсов: открывается офлайн,
вкладывается в тикет,.diff-ится построчно. Код возврата: 0 — схема готова;
1 — findings не прошёл валидацию; 2 — `.process` не читается.

## Пайплайн (обязательный порядок)

1. **Найти баги** — ревью по `references/reviewing-a-process.md`:
   `lint_process.py` (объективные дефекты) + `structure_audit.py` (GOTO/хабы)
   + чтение смысла. Решение «баг или нет» принимает ревьюер, не рендерер.
2. **Составить `findings.json`** (схема ниже) — ВСЕ найденные баги одним
   файлом, не по одному: нумерация и картинка строятся по всему списку сразу.
3. **`flow_diagram.py --findings`** — валидация схемы, детерминированная
   нумерация, рендер.
4. **Показать HTML** и вести разбор по номерам: «баг №2 — блок 5a0e99e8».
   Номера в схеме, легенде и разговоре — одни и те же.

Пайплайн детерминирован: один `.process` + один `findings.json` → байт-в-байт
один HTML (проверяется `--check` и тестами). В выводе нет времени, случайных
id и абсолютных путей — только имя входного файла.

## Схема findings.json

```json
{
  "findings": [
    {
      "severity": "P0",                      // P0 | P1 | P2 — как в линте
      "title": "Письмо молча не уходит при $null во вложениях",
      "where": ["5a0e99e8"],                 // красные метки: блоки бага
      "what": "Attachments=$Items_files остаётся $null у первого
               сообщения без вложений; шаблон блока вызывает
               $Attachments.GetType() → исключение, ErrorLevel=Ignore
               глотает его — письмо не уходит, поток идёт дальше.",
      "fix": {                                // необязательно: не всякий
        "text": "Инициализировать $Items_files пустым List в начале
                  процесса; ErrorLevel=Ignore сменить на Handle.",
        "where": ["5a0e99e8"],               // зелёные метки на существующих блоках
        "insert_after": ["f360222a"],        // зелёный блок «НОВЫЙ» после этого блока
        "insert_title": "InvokeExpression: инициализация $Items_files",
        "insert_code": "$Items_files = New-Object System.Collections.ArrayList"
      }
    }
  ]
}
```

Правила полей:

- `severity`, `title`, `where`, `what` — обязательны. `title` ≤ 120 символов,
  `where` — непустой список.
- Ссылка на блок — полный UUID или префикс ≥ 8 символов. Префикс обязан
  разрешаться ровно в один блок: нет совпадений — `FD-REF-001`, несколько —
  `FD-REF-002` (с кандидатами). Валидация падает до отрисовки — схема с
  «висячей» меткой не выпускается.
- `fix` необязателен целиком; внутри него обязателен только `text`.
  `fix.where` — какие существующие блоки менять, `insert_after` — после каких
  блоках вставить новый (зелёный пунктирный узел с `insert_title`/`insert_code`
  размещается справа от якоря).
- Один блок может быть меткой нескольких багов (и красной, и зелёной) —
  метки нумеруются и не смешиваются.

## Нумерация (правило канонического порядка)

Номера назначает рендерер, а не автор JSON: находки сортируются по
`(P0 < P1 < P2, верхний-левый блок where, id блока, title)` и нумеруются 1..N.
Один и тот же набор багов даёт одни и те же номера при любом порядке записей
во входном JSON — на номера можно ссылаться в переписке и в тикетах.

## Что рисуется

- Узлы — на координатах из самого `.process` (`Left`/`Top`): схема повторяет
  холст Designer, разработчик узнаёт свою диаграмму. Тип блока + DisplayName,
  выключенные блоки — серые с пометкой «OFF».
- Связи — линия со стрелкой и именем исходного порта (`Yes`, `Next`, `Row`,
  `Error`…); стрелка назад (вверх по холсту) — кривой, чтобы не сливалась с
  прямым потоком.
- Красная метка N — кружок с номером у левого верхнего угла блока бага;
  зелёная метка N — у правого верхнего угла блока правки; зелёный пунктир —
  вставляемый блок. Ниже — легенда: карточка на каждый баг (серьёзность,
  где, что сломано, как чинить).

## Границы

- Схема — навигация и разбор, не доказательство: рантайм-выводы (что реально
  упало в исполнении) в `what` помечает ревьюер, инструмент их не проверяет.
- Правка файла по-прежнему идёт своим сценарием
  (`references/editing-existing-process.md`): findings.json — это отчёт,
  не спецификация `apply_spec.py`.
- Очень широкие холсты не пересобираются в колонки: сохраняется авторская
  геометрия, прокрутка — панелью браузера.
