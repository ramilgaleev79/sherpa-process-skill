# Ревью чужого `.process` (ничего не меняем)

Сценарий ревью отвечает на вопрос «что в этом роботе сломается и где», а не «как
переписать». Файлы в ходе ревью **не правятся**: правка — отдельный сценарий
(`references/editing-existing-process.md`) со замером радиуса и бэкапом.

Основа чек-листа — ревью многослойных проектов из сотен блоков.
Машинно проверяемые пункты вынесены в `scripts/lint_process.py`;
оставшееся требует чтения смысла и оставлено в чек-листе.

## Инструменты (три, по возрастанию «сколько думать»)

| Инструмент | Отвечает на вопрос | Что даёт |
|---|---|---|
| `scripts/lint_process.py FILE` | «что объективно дефект» | находки `LNT-*` с P0/P1/P2, сводка по структуре |
| `scripts/structure_audit.py FILE` | «где управление держится на GOTO» | классы стрелок, GOTO назад/наружу/вглубь, хабы, глубина, горячие переменные |
| `scripts/golden_inspector.py FILE --deep` | «что внутри конкретного блока» | свойства, порты, версии, декодированные Base64-контейнеры |

Порядок: линт → структура → инспектор только для спорных блоков → чтение смысла.
Линт и аудит работают без Designer и без зависимостей (только stdlib).

## Чек-лист (что искать в чужом сценарии)

| Что искать | P | Чем | Признак в тексте |
|---|---|---|---|
| Секреты в открытом виде: пароль SMTP, `Bearer …`, `gsk_…`, hex-токен ≥32, `token=` в URL | **P0** | `LNT-SEC-001` | значение свойства/переменной не ссылка `$Var`, а литерал |
| `http://` во внешнем вызове (токен и данные уходят открытым) | P1 | `LNT-SEC-002` | URL со схемой http |
| Выключенные блоки внутри рабочей ветки (`IsEnabled=false`) | P2→P1 | `LNT-EDGE-004` + глаза | ветка держится на выключенных блоках |
| GOTO-эквиваленты: `AbortContainer`, `FullAbort`, стрелка назад, флаг + проверки в разных местах | P1 | `structure_audit.py` | классы `goto-*`, хабы, `$needStop` |
| Мёртвый код: недостижимые от `Старт` блоки | P2→P1 | `LNT-GRF-001` | «перезапуск через 12 часов» рядом с рабочей ветвью |
| Обрывы потока: из блока нет пути к `Конец`/`Прервать` | P1 | `LNT-GRF-002` | терминатор потерян при копировании |
| Обработка ошибок: `ErrorLevel=Handle` без подключённого выхода `Error` | P1 | `LNT-EDGE-002` | ошибка глотается молча |
| Двойной механизм ошибок: `FullAbort` **и** ручные вызовы обработчиков, `1/0` как управление циклом | P1 | глаза + `structure_audit` | несколько записей об одном инциденте |
| Открытые порты/соединения: порт + `UseSSL`, implicit TLS | P1 | глаза (`port 465` = SSL, `587` = STARTTLS) | письма «не уходят», но процесс зелёный |
| Интерактивные блоки в сервисе (`MessageBox`, `FolderBrowserDialog`, `InputBox`) | P1 | `LNT-UI-001` | в неинтерактивной сессии диалог некому закрыть |
| PS-эмуляция типа: регулярки вместо `[decimal]::Parse`, конкатенация JSON, `(1/0)` | P1 | `golden_inspector.py` + глаза | неверный результат на части данных |
| Контракт робота: `InParams`/`OutParams` в `.sherpa`, перезапись входных параметров | P1 | глаза | то, что передал оркестратор, затирается |
| Legacy-версии блоков (версия старее каталога) | P2 | `LNT-CAT-002` | свойства читать по текущему шаблону |
| Блок вне каталога (удалён/переименован в 1.4.4) | P1 | `LNT-CAT-001` | `LaunchChrome`, `NewFile`, `RecognizeCaptcha` |
| Необъявленные переменные, общий scope между диаграммами | P2 | `LNT-VAR-001` | переименование переменной ломает всё молча |
| Копипаста: одинаковые `InternalName`+`DisplayName` | P2 | `LNT-GRF-003` | три одинаковых конвейера проверки ИНН |
| Гигиена проекта: `.backup/`, `.robot`-сборка, `*.tmp`, промпты вне проекта | P2 | глаза | артефакты и «чужая» папка в зависимостях |

## Порядок ревью

1. **Инвентарь.** Список диаграмм, число блоков/связей, что вызывается из чего
   (`ProcessContainer`), где входные параметры робота. Это оглавление отчёта.
2. **Линт по всем файлам.** P0 читать построчно, P1 — все, P2 — по одному
   примеру на класс (их много и они однотипны).
3. **Структура на главной диаграмме.** `goto-*`, хабы, глубина, горячие
   переменные: тут видно, почему «локальная» правка в этом сценарии невозможна.
4. **Смысл.** По чек-листу пройти пункты «глазами»: схема потока, обработка
   ошибок, контракт, промпты, валидация данных, логирование.
5. **Приоритеты и план.** Сначала P0/P1 с внешним эффектом (безопасность, потеря
   данных), потом сопровождение. Каждый пункт — с планом действий, а не «надо
   подумать».

## Шаблон отчёта

Отчёт адресован владельцу робота: сначала риск, потом как чинить. Каждый пункт
обязан иметь локацию (`файл`, `блок` + короткий ID) — дефект без локации не
дефект.

```text
# Ревью <проект> (Sherpa RPA 1.4.4)

**Что смотрел:** <проект> — <N> диаграмм `.process` (<блоков>, <связей>),
промпты, сборка, бэкапы.
**Как смотрел:** `lint_process.py` (P0 <n>, P1 <n>), `structure_audit.py`
(GOTO <n>, хабы <n>), `golden_inspector.py` для <блоки>; Designer не запускался —
поведение выведено из шаблонов блоков.

## 1. Что это за проект
<один абзац: назначение, вход/выход, схема потока текстом>

## 2. Что сделано хорошо
<2–5 пунктов: идемпотентность, валидация входа, разделение ошибок>

## 3. Критично (P0)
### 3.1. <название>
<где: файл, блок, свойство>. <почему это дефект>.
<что сделать>

## 4. Важно (P1)
1. **<название>.** <где>. <последствие>. <что сделать>.

## 5. Желательно (P2)
- <сопровождаемость, наблюдаемость, гигиена>

## 6. Приоритетный план
**Неделя 1 — <тема>:** <пункты>
**Неделя 2 — <тема>:** <пункты>
**Месяц — <тема>:** <пункты>

## 7. Оценка
| Критерий | Оценка | Комментарий |
|---|---|---|
| Работоспособность | n/10 | … |
| Качество данных | n/10 | … |
| Безопасность | n/10 | … |
| Сопровождаемость | n/10 | … |
| Наблюдаемость | n/10 | … |

## 8. Что не проверялось
<что требует запуска Designer/рантайма и почему вывод не делался>
```

## Границы

- **Серьёзность в отчёте — по последствию, а не по коду линта.** Линт даёт базу
  (P0/P1/P2), но он не знает контекста: выключенный блок вне рабочей ветки — P2,
  а выключенный блок, на котором держится повторная итерация, — P1. Повышайте
  осознанно и объясняйте в пункте.
- **Не выдумывать рантайм.** Если вывод зависит от поведения рантайма (как
  обходится выключенный блок, наследуются ли переменные между диаграммами,
  что делает `AbortContainer` на верхнем уровне) — писать это в раздел «что не
  проверялось», а не выдавать за факт.
- **Не смешивать ревью и правку.** Найденное — в отчёт; правка отдельно, по
  спецификации, с `change_impact.py` → `apply_spec.py` → `process_diff.py --expect`.
- **Severity по последствию, а не по вкусу:** P0 — утечка секрета/потеря данных/
  невоспроизводимость; P1 — неверный результат на части входов; P2 —
  сопровождение и наблюдаемость.
- **Секреты не перепечатывать** в отчёт целиком: «SMTP-пароль в блоке …» без
  значения; значение только имя/длина. Инструменты это соблюдают: `lint_process`
  печатает класс и место, `apply_spec`/`process_diff` показывают у секретных
  свойств «секрет скрыт», `validate-ir` — класс секрета (`SHP-GEN-004`).


## Автосейвы Designer (`~имя.process`)

Designer периодически пишет рядом с рабочим файлом скрытую копию `~<имя>`
(`AutoSaveProcessed` — IL-verified). Это не авторский контент: состояние
могло разойтись с файлом. В ревью такие файлы не подставлять, в корпус не
включать; lint помечает их `LNT-BAK-001`. Если ревьюят папку проекта —
просьба к автору: открыть-закрыть файл в Designer (автосейв обновится) или
удалить остаток.
